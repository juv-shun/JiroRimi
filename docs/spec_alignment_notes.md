最終更新: 2026-03-08

## 目的

設計書と実装の差分について、会話で認識合わせした内容を記録する。
この時点ではコード修正は行わず、どちらを正とするか、設計書更新で吸収するか、改善課題として扱うかを整理する。

## 整理ルール

- `実装が正`: 実装に合わせて設計書を更新する
- `未実装バックログ`: 設計済みだが未実装であり、不整合ではない
- `改善課題`: 直ちに不整合とはせず、今後の整理・リファクタリング対象として扱う

## 認識合わせ済み項目

### 1. ランキング画面

- 区分: 未実装バックログ
- **ステータス: 対応不要**（実装時に設計書と突き合わせる）
- 結論: 不整合ではない
- 理由:
  - 設計書上は仕様定義済み
  - バックログでは未着手
  - 実装は未作成
- 対応方針:
  - 問題点としては扱わない
  - 「設計済み・未実装項目」として管理する

### 2. ログイン後の遷移先

- 区分: 実装が正
- **ステータス: 設計書更新済み**
- 結論: 設計書を更新する
- 現在の正しい挙動:
  - ログイン後はいったん `/` に遷移する
  - プロフィール未完了の場合は `/mypage` に誘導される
  - プロフィール完了済みユーザーは `/` に着地する
- 対応方針:
  - 設計書の遷移先記述を `/` 基準に修正する
  - 初回登録時は `/` 経由で `/mypage` に誘導されることを明記する

### 3. `x_id` の必須性と `PENDING` 運用

- 区分: 実装が正
- **ステータス: 設計書更新済み**
- 結論: 設計書を更新する
- 現在の正しい方針:
  - `x_id` は初回プロフィール作成時に未確定状態を許容する
  - nullable や暫定値を許し、アプリ層でプロフィール完了判定を行う
- 対応方針:
  - DB設計書の `x_id` 必須前提を見直す
  - アプリ層で完了判定する設計を明文化する

### 4. 仮結果の多数決ロジック

- 区分: 実装が正
- **ステータス: 設計書更新済み**
- 結論: 設計書を更新する
- 現在の正しい方針:
  - 投票は自チーム視点で解釈する
  - `win` だけでなく、相手チームの `lose` も反映して仮結果を算出する
  - 仮結果は参考情報であり、最終結果は管理者が確定する
- 対応方針:
  - 仮結果算出ロジックを実装準拠で設計書へ反映する
  - 仮結果は参考情報であることを明記する

### 5. 大会一覧のボタン表示方針

- 区分: 実装が正
- **ステータス: 設計書更新済み**
- 結論: 設計書を更新する
- 現在の正しい方針:
  - エントリー、チェックイン、ロビーの各ボタンは常時表示する
  - 条件未達時は非活性で状態を示す
- 対応方針:
  - 「表示なし」前提の記述を見直し、常時表示 + 活性/非活性表現へ修正する

### 6. エントリー一覧でのチェックイン情報公開タイミング

- 区分: 実装が正
- **ステータス: 設計書更新済み**
- 結論: 設計書を更新する
- 現在の正しい方針:
  - チェックイン人数と各参加者のチェックイン状態は `checkin_start` 以降に公開する
  - ログイン状態や本人のエントリー有無とは無関係で、時間条件のみで公開する
- 対応方針:
  - 画面設計書に公開タイミングを追記する

### 7. 参加者試合画面の確定結果表示文言

- 区分: 実装が正
- **ステータス: 設計書更新済み**
- 結論: 設計書を更新する
- 現在の正しい方針:
  - 参加者には自分視点で `勝利 / 敗北` を表示する
- 補足:
  - 差分は表示文言・表示視点の違いであり、結果データそのものの差ではない
- 対応方針:
  - 画面設計書の文言を参加者視点表現に合わせる

### 8. イベント開始時の初期除外ルール

- 区分: 実装由来の重要仕様
- **ステータス: 設計書更新済み**
- 結論: 設計書へ追記する
- 現在の正しい方針:
  - 参加人数を10人単位に合わせるため、余剰人数分はチェックイン時刻が遅い参加者から初期除外候補として選ばれる
  - 最終的な除外対象は運営者が変更できる
- 対応方針:
  - 運営フローまたはイベント開始仕様に追記する

### 9. `/` トップページと `Home` ナビ

- 区分: 実装由来の重要仕様
- **ステータス: 設計書更新済み**
- 結論: 設計書へ追記する
- 現在の正しい方針:
  - `/` は正式なトップページとして存在する
  - 共通ナビゲーションに `Home` が存在する
  - `/` は大会一覧そのものではなく、サービスのトップ / 案内ページとして扱う
- 対応方針:
  - 画面一覧、画面遷移、ナビゲーション仕様に反映する
  - `/tournaments` とは別画面として定義する

### 10. ラウンド状態と `team_assignment` / `waiting` の関係

- 区分: 改善課題
- **ステータス: 未対応**（将来リファクタリング候補）
- 結論: すぐに不整合とは扱わない
- 現状認識:
  - 体験としては「チーム編成完了 = 試合開始」に寄せたい
  - 実装上は `team_assignment` 後に `waiting` を経由する構造が残っている
  - 現在の挙動は成立しているが、状態遷移としてはやや分かりにくい
- 対応方針:
  - 将来のリファクタリング候補として整理する
  - 状態モデル、UI、APIフローをまとめて単純化する方向で検討する

### 11. 共通レイアウト（ヘッダー / サイドバー / フッター）

- 区分: 実装が正 + 一部改善課題
- **ステータス: 設計書更新済み・リファクタリング完了**（未使用 `Header` コンポーネント `app/components/header.tsx` を削除済み）
- 結論:
  - ナビゲーションの中心はサイドバーが正
  - フッターは不要
  - 未使用の `Header` コンポーネントは将来的に削除したい
- 現在の正しい方針:
  - 共通ナビゲーションはサイドバー中心で構成する
  - ヘッダー中心の設計記述は古い
  - フッターは現時点では仕様不要
- 対応方針:
  - 設計書の共通レイアウト記述をサイドバー中心に更新する
  - フッター記述は削除または不要として整理する
  - 未使用 `Header` コンポーネントはリファクタリング候補として別管理する
