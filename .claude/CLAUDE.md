# Jiro-Rimi Cup

ポケモンユナイトのソロ大会運営Webアプリケーション。

## 概要

エントリー管理・スイスドロー式チーム分け・試合進行・成績管理を一元的に提供し、年間を通じた継続的な大会開催を支える基盤。

## 大会の種類

- **ボーイズ じろカップ**: 男子ソロ大会
- **ガールズ りみカップ**: 女子ソロ大会
- 同日開催（昼: ボーイズ / 夜: ガールズ）

> **方針**: イベント単位でオプショナルに性別制限を設定可能。`events.gender` に `"boys"` / `"girls"` を設定すると、該当性別のユーザーのみエントリー可能（RLS・API・UIの3層で検証）。`null` の場合は制限なし。

## 大会構造

```
大会
├── 予選1〜N（回数は大会ごとに設定可能）
└── グランドファイナル（上位20名によるダブルエリミネーション）
```

## ユーザー種別

| 種別 | 権限 |
|------|------|
| 未ログイン | 閲覧のみ |
| 参加者 | エントリー・チェックイン・勝敗入力 |
| 運営者 | 大会作成・管理・試合進行操作 |

## 主要機能

- Discord認証によるログイン
- プロフィール設定（プレイヤー名、X ID、性別、ロール優先順位）
- 予選単位のエントリー・チェックイン
- AIによるロール考慮のスイスドロー式チーム分け
- 試合進行管理（ロビー番号入力、勝敗入力）
- 成績・ランキング表示

## テスト戦略（最小構成）

個人開発の速度を落とさず、大型リファクタリング時の事故を防ぐために、テストは「少数・高価値」を原則とする。

### 方針

- 目的は網羅率ではなく、主要仕様の破壊検知。
- まずユニットテストを優先し、APIは重要分岐のみを契約テストとして追加する。
- E2Eは当面実施しない（必要性が出た時点で再検討）。
- 不具合を修正したときは、同種の再発防止テストを1件追加する。

### テストレイヤー

- Unit（最優先）: 純関数・バリデーション・状態判定を対象にする。
- API Contract（必要最小限）: ステータスコードとエラーメッセージの契約を固定する。

### 初期対象（この順で作成）

- エントリー/チェックインのボタン状態判定ロジック
- `zod` バリデーション（プロフィール・大会/イベント）
- 日時変換ユーティリティ
- プロフィール完了判定
- エントリーAPI・チェックインAPIの主要分岐（未認証、入力不正、期間外、権限系、重複系）

### 目安件数

- Unit: 20〜30ケース
- API Contract: 8〜12ケース
- 合計: 30〜40ケースで開始

### 実装ルール

- テストしづらいコードは、先に純関数へ切り出してからテストを書く。
- DBや外部サービス依存はモックし、テストは高速（数秒〜十数秒）を維持する。
- 大型リファクタリング前に既存挙動を固定する Characterization Test を先に書く。

### 運用ルール

- プランモードの計画時には、テストコードを追加するかを必ず判断し、追加する場合は対象（何を）・観点（何を保証するか）・実行方法を計画に明記する。
- プランモードでの実装完了後、コミット前に最低1回テストを実行する。
- 仕様変更がある場合は、実装より先にテスト期待値を更新する。
- テストが重くなったら、価値の低いケースから削減する（ゼロにはしない）。
